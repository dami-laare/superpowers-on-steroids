# Closing GitHub Issues

## Overview

A closing comment **states the verdict, proves it in the fewest lines that hold, and hands off deployment** — in that order. It is not a status update, and it is not a narrative of your investigation. Lead with the answer; compress the evidence to results.

The failure this skill prevents is a **bloated, walkthrough-shaped reply** — headed sections narrating what you did, evidence tables, insight boxes, hedging. The fix is to fill a fixed contract, not to write freely and trim.

Pick the tier by outcome:

- **Shipped a code fix** → the headed multi-section form below.
- **Won't-fix / reclassify / no-defect / third-party** → the short form: bold verdict line + 3–6 tight paragraphs. This is the common case.

(A full formal RCA with appendices is a *separate* mode, used only for customer-facing high-severity post-mortems — not the everyday close.)

## Contract A — shipped-fix form (sections, in this exact order)

1. **Title line = the verdict.** `## ✅ Fixed, released in <ver>, verified on <env>` or `## Resolved — <one-line what>`. The status lives in the heading; do not restate it in prose.
2. **Root cause.** One tight paragraph. Mechanism traced to `path/file.ext:LINE`. State whether it is a **latent/long-standing defect or a regression** (if a regression, name the introducing commit + date).
3. **The fix / what changed.** `org/repo#NN` **plus the merged commit SHA**. What the code now does, and **why this approach over the obvious alternative**.
4. **Verification.** What was tested, on which env, test counts — as a small table or a one-line result (`6 findings → 0`, `0 restarts over 11h`). Confirm the fix lives in the **deployed artifact/tag/image, not just source or green CI**. Explicitly label anything **not yet proven**.
5. **Release + deployment handoff.** Version/RC tag, the **Jira CR** number, and the standing line: **SaaSOps executes the prod deploy; Engineering does not touch prod/infra.** Keep `merged ≠ released ≠ activated` explicit — never imply prod-fixed when it is only merged or staged.
6. **Out of scope.** What this deliberately does not cover → spin a separate issue.

## Contract B — reclassify / won't-fix / no-defect form

- **First line is the bolded verdict:** `Root cause found, and it is not the <X> the auto-triage flagged.` / `operational, not a code bug.` / `no defect found — closing.`
- **3–6 short paragraphs:** what is actually happening (read live, with real ids/metrics) → why it is not a code fix on our side → **the real owner + the concrete ask** (open a DevOps/SaaSOps/third-party ticket).
- If the drone/auto-triage opened a draft PR, **close it explicitly and say why.**

## House conventions (both forms)

- **Ratify or overturn the drone triage explicitly** — never silently ignore it or its draft PR.
- PRs as `org/repo#NN`; releases as bare version tags; prod deploy always deferred to a **named CR** owned by SaaSOps.
- First person, past tense for findings, present tense for current state. Blunt, evidence-first, opinionated on disagreement.
- End an AI-authored comment with the house footer.

## What a closing comment is NOT

| Off-house (my instinct) | House |
|---|---|
| Headed walkthrough narrating the investigation | Verdict first; investigation compressed to results |
| Restating the issue body / thread before answering | Jump straight to verdict/root cause |
| Evidence table + step-by-step verification narration | One result line or one small table |
| Insight boxes, confidence %, emoji beyond one ✅/⚠️ | Dense, unornamented prose |
| "Fixed in #NN, closing." (bare pointer) | Root cause to `file:line` + why-not-a-regression |
| "Tests pass, done." | Fix confirmed in the deployed artifact; unproven parts labeled |
| Implies prod-fixed when only merged | `merged ≠ released ≠ activated`, deploy handed to a CR |
| Effort/time editorializing ("took a while", "ships next week") | Omit entirely; timing only as "tracked under CR X" |

## Quick reference — exemplar (tight structured close, verbatim shape)

```
Status: remediated and released. Closing.

Fix
- Lithium-LGR#28 (merged): log4j 1.2.14 → reload4j 1.2.26; R01.06.01.10 → .11.
- Lithium-RELEASE#576 (merged): LGR pin .09 → .11; NewNet release v24.03.24.15.

Verified
- .09 → .11 on full-stack appliance clone: live UI under reload4j, zero log4j-1.2*.
- Scanner delta: 6 log4j CVE findings → 0.

Closing — remediation shipped and verified in v24.03.24.15. Customer-side deploy
on affected nodes + authenticated rescan tracked under ka#60450734.

🤖 Generated by Claude.
```

## Red flags — you are writing the wrong shape

- You wrote a `###` section explaining *how you investigated* → cut it; keep the result.
- You built a table to show verification *steps* → collapse to one result line.
- The verdict is not in the first line/heading → move it up.
- You referenced a PR without its merge SHA, or claimed a fix without saying where it's deployed → add them.
- You didn't mention the drone triage or its draft PR → ratify/overturn + close it.
- You reached for an insight box, a confidence score, or a second emoji → delete.
